# 学习使命（learning-mission）

> 生成日期：2026-08-12　流程：sdd-learning 章程阶段

## 一句话目标
**从零搭建一份与官方脚手架逐文件 diff 零差异的苍穹外卖 Maven 工程**，并在搭建过程中真正理解"一个 Spring Boot 项目为什么长这样"。

## 为什么学这个（背景与动机）
- 苍穹外卖教程的核心教学点在于**脚手架搭建与项目结构设计**，而非代码细节——在 AI vibecoding 时代，能看懂、能设计、能指挥的项目结构能力比手写代码更重要。
- 本复刻产物（`scaffold-build/sky-take-out/`）将作为**后续功能开发（SDD vibecoding）的基底**：接口、数据库、前端全部对齐官方，无缝衔接后续开发。
- 两个阶段性效果：
  - 效果一：用自己的 SDD 工作流搭完脚手架，之后直接 vibecoding 开发剩余功能模块；
  - 效果二：具备从零独立设计项目架构、做技术选型的能力，能构建完整项目。
- 附带目标：顺带学透 git 管理（分支、提交、合并）；整个学习过程本身就是一次 vibecoding 实践。

## 成功标准（如何证明学成了）
1. **内容一致复刻**：复刻产物与官方参照物逐文件 diff，**实质内容一致即通过**（目录结构/包名/类名/配置/行为；XML 元素顺序与空行/换行符差异放行——不影响成品效果）；出现缺内容、写错（坐标/类名/配置等）等可能导致成品与模板不一致的根本性差异才需修改。diff 范围 = `pom.xml` ×4 + `src/`，排除 `.idea/`、`target/` 等产物。
2. **跑通验证**：MySQL 建库（`sky_take_out`）→ 启动 `SkyApplication` → 管理端员工登录接口返回正确结果 → 服务日志无异常。
3. **理解达成（费曼）**：能向老师完整讲出（**复现与设计并重**：对照参照物逐文件写对、diff 一致是验收标准；能讲出"为什么这样设计"的设计动机与取舍是学习重点）：
   - Maven 多模块工程的组织方式（父 pom 管什么、子模块怎么依赖）；
   - Spring Boot 启动流程（启动类 → 自动配置 → Controller/Service/Mapper 怎么被装上）；
   - 员工登录这条链路从 HTTP 请求到数据库的完整旅程（Controller → Service → Mapper → MySQL，拦截器 + JWT 怎么夹在中间）；
   - 各模块（common/pojo/server）的职责边界，以及 DTO/Entity/VO 为什么分开；
   - 各包/模块的**划分设计**：为什么这些内容放公共层、8 包如何按职责分类（契约 / 配置转换 / 状态能力）、有状态（context）与无状态（utils）的分离原则。
4. **学习闭环**：每单元走完规划→实施→验证→合并，验证环节不偷懒（费曼检验 + 亲手跑通 + 独立审查 AI 代码）。

## 学习范围（交付边界）
- **复刻对象**：仅 `backend/sky-take-out/` 官方脚手架（架构完整、业务仅员工登录）。
- **只读资源**（不复制、仅引用）：数据库脚本 `database/sky.sql`、接口文档 `interface/*.json`、数据库设计文档、课程讲义/PPT/完整版代码（功能开发阶段的审查基准）。
- **不做**：前端工程、接口 JSON 文件、数据库设计文档的复刻；不提前开发员工登录之外的业务。

## 技术栈（复刻目标）
Spring Boot 2.7.3（Java 17 编译目标，本机先用 JDK 21 试跑）、MyBatis 2.2.0、MySQL 8、Druid、Redis（暂不装）、JWT(jjwt 0.9.1)、Lombok、knife4j 3.0.2；了解级：阿里云 OSS、POI、WebSocket、微信支付 SDK。

## 教学协作约定（老师必须遵守）
- **推进节奏由用户明确确认，不由老师自行判断**：
  - 费曼检验通过（用户一次性回答正确、答案中不含疑问句）→ 老师可直接进入下一知识点；
  - 用户回答有错、或给出部分解答并提出疑问 → 老师解答后**不得直接推进**，必须等用户答案不再含疑问句、并明确说出"明白了/继续"，才进入下一知识点。
- 讲解与费曼检验交替进行，禁止答完疑问后跳步赶进度——本使命原则"理解优先，速度其次"。
- **大块内容分块推进**：任务组内的大块讲解（如 pom 多块结构）按块细化为学习小阶段，每块一阶段、逐块费曼确认；用户可随时要求进一步细化粒度，老师不一次性倒完。
- **开场抽查（间隔验证）**：每个学习单元开始时（新会话），老师先随机抽查**上一单元**的 2-3 个核心知识点（不提示、不剧透）；答不出/不准确 → 先补学再开始新单元。目的：对抗遗忘曲线、区分"真懂"与"复述"。
- **课程总验收（反转课堂式，可选）**：全部单元完成后，用户**可选择**进行一次整体验收——把全部知识点（可按模块拆分）**讲给老师听**，老师提问检验。目的：反向暴露盲区，验证真实掌握度。非强制环节。
- **知识沉淀（Obsidian 笔记）**：触发条件两条，满足其一即记录进 Obsidian 仓库 `E:\deeplearning\dl\Java`：
  1. **知识点切换文件/代码类型**时（如 pom.xml 知识 → .java 注解知识）——防止上下文过长导致笔记质量不佳；
  2. **大阶段（roadmap 里程碑）完成**时——整段学习经验与知识总结。
  **记录更新完成后，才进入下一步**（新知识点/下一阶段）。

**笔记书写标准（Obsidian 笔记规范）**：
- **定位**：笔记是复习教材，不是课堂讲义；类比是课上理解的手段，不作为笔记知识本体。
- **内容原则**：
  1. 官方术语为主体：用规范定义写（构件、聚合/继承、Reactor 等），不用类比讲故事；
  2. 知识点结构 = 定义 → 详细说明 → 示例（代码/表格）；
  3. 背景补充用正规方式（历史背景、痛点、成因），不用"包工头/货架"式叙述；
  4. 困惑与答案（FAQ）是重点：记录学习过程中的真实困惑，答案用规范术语写；
  5. 类比使用受限：极少量可作"助记"（明确标注），禁止类比与术语混写导致不知所云；
  6. 不含学习流程语境：验收、费曼、diff 等教学场景内容不进笔记。
- **结构模板**：标题+元信息（来源单元/日期）→ 编号知识章节（定义→说明→示例）→ FAQ 章节 → 常见错误章节 → 附录：完整示例（带注释）。
- **写作流程**：AI 起草 → 用户审阅修改 → 确认通过 = 沉淀完成（之后才进入下一步学习）。

## 学习流程（怎么学）
sdd-learning 规范驱动学习：章程阶段（本文档体系）→ 学习单元循环（规划→实施→验证→合并）→ 复盘。每单元独立 git 分支、小步提交；每单元三件套文档（plan / learning-goals / check）先在 `learning-specs/<日期>_<单元名>/` 生成，经审查后实施。
